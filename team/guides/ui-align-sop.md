# UI 对齐 SOP（人读端到端流程）

> **归属**：`PROTOCOL §⑨.1`（UI 保真度：原型即契约）。本文件是该条所引用的 **SOP 全文**，落于稳定路径（`~/.openclaw/team/guides/ui-align-sop.md`），供人读端到端执行。
> **维护者**：**Jobs**（审美与 UX/UI 质量门禁责任人）。改动须与下列正文保持一致，不得冲突。
> **单一事实源（本文只引用、不复制）**：

> - 机检引擎与清单 schema（`.ui-align.json`、`<page>.json`、check 词汇表、computed style、退出码、接入、安全模型、已知边界）→ `tools/ui-align/README.md`；
> - 断言产物契约（选择器清单 JSON + runner 判定）→ `guides/ui-align-assert-spec.md`；
> - 相关红线：原型禁写实现 → `PROTOCOL §⑨.2`；文档引用规范 → `PROTOCOL §⑥.1 第 11 条`；可机检门禁落点 → `PROTOCOL §⑳.1`。
> **引用规范**：一律写「文档名 §章节名」，**不写行号锚点、不写卡号锚点**（沿用 `§⑥.1 第 11 条`）。

## 1. 一句话原则

**原型（设计稿）是实现的设计基线契约，不是参考资料。** 凡原型已有的 UI，实现必须**逐区块对齐**；任何偏离都必须在卡内**书面说明理由并经 Elon 批准** —— 禁止静默简化、禁止自造原型没有的结构。

> 本 SOP 解决的是「原型 → 实现」这一段的一致性：把还原度从**主观印象**变成**可枚举（区块清单）、可复现（断言脚本）、可判定（机检 + 截图双核）** 的流程。

---

## 2. 三条防线总览（谁 / 何时 / 出什么 / 怎么判）

每张 UI 卡都必须走完三层；缺任一层即未完成。

| 防线 | 时点 | 责任 | 产物 | 判定 / 证据 |
|---|---|---|---|---|
| **事前·结构契约** | 卡开工**前** | **Jobs**（Elon 建卡派单） | 该页**结构契约**：枚举原型**全部区块**（区块名 / id / role / `data-*` + 选择器）+ 数据契约标注 + 可机检验收点；落 `workspace/<task-id>/`（清单 JSON，契约版） | 区块清单**含「一致」项**（防漏项）；**无行号锚点**；作为卡 Acceptance 的机检条件来源 |
| **事中·结构断言** | 开发完成时 | **Linus** | 选择器断言脚本产物（`ui-selectors.json` + runner），用 `tools/ui-align` 跑通 | 断言**不过 ⇒ 卡不许置 ready/交付**（`§⑨.1` 硬门槛） |
| **事后·截图对照** | 验收时 | **Turing**（机检复跑，独立）+ **Jobs**（视觉认证）；**Elon** 终审亲看截图 | 断言复跑报告 + **同视口 × 同主题 × 同语言**截图对照（原型 vs 实现） | 双核：机检 + 视觉；Elon **必须亲自比对截图**，不得只凭「接口通/构建过/worker 自述」 |

> 说明：三层的「时点」是**门禁位**——事前契约没出，开发不该开工；事中断言没过，卡不该交付；事后对照没做，Elon 不该置 done。

## 3. 端到端流程（按阶段）

### 阶段 A · 拆卡前（Elon）
- **核在途段脏面文件**：同一文件的 UI 卡必须串行，避免「同文件双卡并发写」（`§⑨.1` 尾注教训）。卡内须显式声明**同文件单写者与串行顺序**。
- **建卡即挂机检条件**：UI 卡 Acceptance 必须物理包含「区块清单（含一致项）+ 机检断言（选择器）+ 截图对照」三条（`§⑨.1` 强化条款）。缺任一条 ⇒ 卡不成立。
- 派的「事前·结构契约」落到 **Jobs**。

### 阶段 B · 事前契约（Jobs）
1. 通读该页**原型**，枚举**全部区块**（不是只列「要做的」，而是**全量**，含已一致项）。
2. 每个区块给出：**区块名 + id/role/`data-*` 语义钩子 + 选择器**；标注**数据契约**（取数来源/字段/状态：加载/空态/错误态）。
3. 产出**可机检验收点**（选择器 + 计数/非空等），结构对齐 `guides/ui-align-assert-spec.md` 的**选择器清单 JSON** 契约（该文件定义产物 schema 与 runner 判定）。
4. 选择器**优先 `data-*` 语义钩子**，**禁依赖 Tailwind class 名**（防换类名断 JS/测试，见 `PROTOCOL §⑥.1 第 11 条` 与 Jobs 的 HTML 路径规范）。
5. 视觉规范：先确认**统一设计风格规范**（`design-style-guide.md`，色板/字体/间距/token 单一事实源）；无则先定，**不得各页自造**（Jobs 为审美与风格唯一裁决者）。

### 阶段 C · 开发中（Linus）
- 按结构契约实现；**原型里已有的区块逐块落地**，偏离须在卡内写明理由并经 Elon 批准。
- **原型文字二义甄别**（`§⑨.1` 附加条款）：原型里的**可见文字**要区分「UI 文案」与「写给开发的注解」（如「（静态占位）」「取数接口待后端」）——**注解不得进界面**；原型侧应以注释/`data-pending` 等**非可见**形式表达「待接入」。
- **原型禁写实现**（`§⑨.2`）：`prototype/**` 是纯设计稿，**禁**在其中写 `fetch`/鉴权/凭据/真实端点；实现一律落真前端工程目录。

### 阶段 D · 事中断言（Linus）
1. 在项目根写 `.ui-align.json`，在清单目录写 `<page>.json`（格式见 `tools/ui-align/README.md` §3 / §4；本 SOP 第 6 节给最小步骤）。
2. 跑 `check.mjs`：DOM 存在性 / 五档无溢出 / console 干净 / computed style 双侧 diff。
3. **断言全过**才允许置 ready 交付；`pending`（未实现）区块在 `--strict` 下计失败 —— 全量清单的意义就是**任何区块都不能悄悄消失**。
4. 结果先落文件（`--json`），Report 附命令 + 退出码 + 摘要。

### 阶段 E · 验收（Turing 机检 + Jobs 视觉 + Elon 终审）
1. **Turing**（独立）复跑断言脚本 + 核验收硬门槛（第 4 节）；**不得复用 Linus 的结论**。
2. **Jobs** 做 UX/UI **视觉认证**：浏览器/工具同视口（1512/1240/980/760/430）× 同主题 × 同语言**截图对照**（原型 vs 实现），逐区块比对；检查是否出现「占位/待后端/TODO」类**可见注解**（出现即打回）。《问题清单》写 `workspace/<task-id>/review/`。
3. **Elon 终审必看截图**（`§⑨.1` 强化条款），确认文档影响判定（`§⑫`）后置终态。

### 阶段 F · 收口
- 逐条勾 Acceptance；**文档影响判定**（涉接口/数据结构/架构/配置/口径 ⇒ 同步文档；否则显式声明「无文档影响」）（`§⑫`）。
- 差异项与遗留写入卡 Report；跨段决策写 `state.md`。

## 4. 验收硬门槛（UI 卡 done 前缺一不可）

对齐 `PROTOCOL §⑨.1`「验收硬门槛」，落地为可操作条目：

1. **区块全清单（含一致项）**：该页**全部区块**都在清单里，**包含已一致的项**（防漏项）；每条差异有「**文件 + 区块名/选择器**」证据（`§⑨.1` 硬门槛 #1）。
2. **机检条件**：修复卡 Acceptance 用**选择器断言（机检条件）**，**不用「看起来像」**。
3. **结构断言脚本全过**。
4. **截图对照**：同视口 × 同主题 × 同语言，**原型 vs 实现**（五档：1512/1240/980/760/430）。
5. **console / page errors = `[]`**；五档**无横向溢出**。
6. **同文件单写者**：卡内显式声明串行顺序（防同文件双卡并发写）。
7. （强化）**Elon 终审亲看截图**；**UI 卡 Acceptance 物理含**「区块清单 + 机检断言 + 截图对照」三条，缺一不得 done。

## 5. 反模式清单（出现即打回）

- 只改局部，**不列区块全清单**。
- 无「文件 + 区块名/选择器」证据的「不一致」结论（凭印象下判断）。
- **自造原型没有的结构**（如用自造组件顶替原型 Hero 卡）。
- **同文件多卡并发写**（不做串行）。
- 以「**构建通过**」替代**视觉对齐验收**。
- 把原型里的**开发注解**（「（静态占位）」等）当文案渲染进用户界面（`§⑨.1` 二义甄别）。
- 在 `prototype/**` 写真实请求/鉴权/凭据，或拿原型页当 E2E 被测载体（`§⑨.2`）。
- 以「接口 200 / 构建过 / worker 自述」替代「**Elon 亲看截图**」。
- 断言未跑或未过就置 ready/交付。

## 6. 与 `tools/ui-align` 对接（引擎与机检规格见 `README.md`）

> 本节只给**接入步骤与落点**；一切字段语义、默认值、schema 细节以 `tools/ui-align/README.md` 为准（§3 配置 / §4 清单 / §5 样式 / §6 用法退出码 / §7 接入 / §9 安全模型 / §10 边界）。

### 6.1 写 `<project>/.ui-align.json`
- **项目知识只允许落在这一个文件**（引擎内零项目路径/端口/选择器）；相对路径相对本文件所在目录（= 项目根）。
- 必填 `manifests`（清单目录）。实现侧二选一：`devServer`（推荐，CI 免手起服务；`cmd` 端口用 `{port}` 占位取空闲端口）或 `implBaseUrl`。
- **强制双侧口径对齐**：`theme`（dark/light）+ `locale`/`localeTag` + `apply`（`htmlAttributes`/`localStorage` 注入，值支持占位）。**必须同主题同语言比**，否则颜色类属性成片「假差异」，真问题被淹没（见 `README.md` §5）。
- 用 `devServer.env` 把项目切到**离线/示例数据态**（很多前端按「环境变量是否为空」区分接入态与离线态；机检要的是结构完整、零请求的离线态）。

### 6.2 写清单 `<manifests>/<page>.json`
- 结构 = 「页 + 区块清单」：一个区块一组断言，每条差异要求 `evidence`；字段/词汇表见 `README.md` §4。
- check 词汇表**只六种**（`selector` / `scope` / `min|max|count` / `nonEmpty` / `desc`），够用且可判定。
- `status`：`delivered`（缺省）或 `pending`（未实现 ⇒ 记 SKIP 并上屏，`--strict` 升级为失败）。
- **从第一天起就是全量**：先写全量区块，未实现的标 `pending` ⇒ 任何区块都不能悄悄消失。

### 6.3 跑 `check.mjs`
- 命令：`node ~/.openclaw/team/tools/ui-align/check.mjs --config ./.ui-align.json [page] [选项]`。
- 产出四类判定 + 一致率：DOM 存在性 / 五档无溢出 / console 干净 / computed style 双侧 diff（+ 人读或 `--json` 报告）。
- **退出码**：`0` 全过 ｜ `1` 断言失败 ｜ `2` 环境/配置/清单错误。样式差异默认**不计入退出码**；要卡门禁加 `--style-strict`。

### 6.4 接 CI
- 建议脚本：`node ~/.openclaw/team/tools/ui-align/check.mjs --config .ui-align.json --json > ui-align.json`。
- **先只卡退出码**（DOM/溢出/console）；**样式稳定后再加** `--style-strict`（避免一次工具升级把下游 CI 一次性判红）。
- **安全模型**（`README.md` §9）：`.ui-align.json` 的 `devServer.cmd` 会被执行，**信任级别等同 `package.json` 的 scripts** ⇒ **不得**在「检出未审核 PR」场景直接跑（`pull_request_target` 类、外部贡献者分支）；此类场景请在**无密钥、断网**的独立 job 跑或先人工审配置。

### 6.5 登记基线
- 首次跑出的数字（区块数 / 断言数 / 失败数 / **样式一致率**）记入项目 README —— 后续回归有对照物（`README.md` §7）。

> 与 trader 的关系：`~/.openclaw`（本仓库）= 引擎与文档；`trader` = `.ui-align.json` + 清单，`ui-align-check.mjs` 仅作**薄封装**转调本工具（断言引擎不重复实现，避免两份实现漂移）。详见 `README.md` §11。

## 7. 证据格式与「一致项也要入清单」

- **证据格式**：每条差异 / 每条断言都带 `evidence` = 「**文件 + 区块名/选择器**」定位（`§⑨.1` 硬门槛 #1）。**文档正文与引用一律不写行号锚点**；工具清单 `evidence` 字段的精确 schema 以 `tools/ui-align/README.md` §4 为准。
- **一致项也要入清单**：清单是**该页全部区块的枚举**，**不含差异也要列**（`status: delivered`）。理由：漏项无法被「只列差异」的方法发现（历史教训 = 区块整块缺失却 5 天无人发现）。「全量清单 + 一致项」是防漏项的唯一手段。
- **判定留痕**：截图对照、断言 `--json` 报告、问题清单均落 `workspace/<task-id>/`（证据不进 inter-session 消息，见 `§⑬` token 瘦身）。

## 9. 已知边界（避免误判）

工具**只比 DOM 事实、不比像素**；computed style 覆盖字体/颜色/盒模型/布局等（不含渐变叠加、阴影合成、抗锯齿）；console 只判实现侧；**需要交互才出现的元素**（开抽屉/切 tab）不在静态断言范围；`settleMs` 是保守静置，图表未收敛时会读中间态。完整清单与「0×0 元素 / 布局连带」读法见 `tools/ui-align/README.md` §5 与 §10。
