# automations/ — framework-owned scheduling (provider-agnostic)

> The framework (`openclaw-team`) **owns team-level scheduling**. Every scheduled
> job is registered by `install.sh` and evaluated by the framework dispatcher
> `dispatch.mjs`; the task provider is only a **callee**. Swapping the provider
> (meerkat-taskpanel → Jira / Plane / Linear / …) does **not** change any scheduled job.

## Files

| File | Role |
|---|---|
| `dispatch.mjs` | Framework dispatcher: `node dispatch.mjs <poll\|patrol\|check-all> [agent]` → prints one line `{"fire":bool, "message"?, "state"?}`. Runs the provider entry **without a shell** and never throws. |
| `providers.json` | Per-provider entry command templates (`{team}` = the deployed team dir, `{agent}` = the agent arg). Ships `meerkat-taskpanel` as the default provider. |
| `README.md` | This file. |

## The dispatch contract

A Gateway trigger script (inline JS, generated by `install.sh` with an absolute
path — **no brace templating**) calls the dispatcher and reads its **last stdout
line**:

```js
const res = await exec({ command: "node <TEAM_DIR>/automations/dispatch.mjs poll linus", timeoutSeconds: 8 });
const r = JSON.parse(String(res?.aggregated ?? res?.stdout ?? res?.output ?? "").trim().split("\n").pop());
// r.fire === true  ⇒ wake the agent (the run turn does the work)
// r.fire === false ⇒ zero-cost idle
// timeoutSeconds bounds the evaluation (exec's own parameter; see "Trigger-evaluation bounds").
```

The provider entry must print a JSON object on its **last stdout line**; the
dispatcher normalizes it generically:

- `fire: <bool>` → used as-is (canonical);
- `stale: [...]` → `fire = stale.length > 0` (patrol convention);
- `ok: <bool>` → `fire = !ok` (health-check convention).

Anything else (missing/invalid `providers.json`, unknown provider, unrunnable or
failing entry, unparseable output) **degrades and exits 0** — a broken provider
must never burn a model turn. What a degrade *says* depends on what the job is
for (T-20261010-190039):

- **action jobs** (`poll` / `patrol`) → `{"fire":false, "state":{…}}` — a failed
  evaluation should simply not wake anyone;
- **the health gate** (`check-all`) → `{"fire":true, "message":…, "state":{…}}` —
  the gate exists to surface failure, so an UNCONFIRMED gate must alarm. Reporting
  `fire:false` there would read "unknown" as "green" and silently drop the warning.
  A non-zero exit is not the gate's verdict on its own: an `{"ok":false}` envelope on
  stdout is recovered first (reason `gate-failed`), because `check-all.sh` prints
  exactly that envelope and then `exit $fail`. A confirmed `ok:true` stays `fire:false`.

## Selecting / swapping the provider

```bash
OPENCLAW_TEAM_TASK_PROVIDER=meerkat-taskpanel   # default
# per-job entry override (no providers.json edit needed):
OPENCLAW_TEAM_POLL_CMD="node /path/to/poll.mjs {agent}"
OPENCLAW_TEAM_PATROL_CMD="node /path/to/patrol.mjs"
OPENCLAW_TEAM_CHECKALL_CMD="bash /path/to/check-all.sh"
```

> **Compatibility (`legacy-name-compat`)**: the pre-rebrand provider name/key `task-panel` still
> resolves — bidirectionally (an old `OPENCLAW_TEAM_TASK_PROVIDER` value *and* a `providers.json`
> still carrying the old key), with a one-line stderr note. The pre-rebrand opt-out flag is likewise
> still accepted as a deprecated alias of `--no-meerkat-taskpanel`.

To add a provider, add an entry to `providers.json`:

```json
{ "my-provider": { "poll": "node {team}/bin/poll.mjs {agent}",
                   "patrol": "node {team}/bin/patrol.mjs",
                   "checkAll": "bash {team}/bin/gates.sh" } }
```

Install-time provider choice: `./install.sh` installs **meerkat-taskpanel** by default;
`--no-meerkat-taskpanel` opts out (bring your own via the ACL).

## ACL coverage & gaps (important)

The ACL (`guides/task-interface.md` §4) defines the **card operations** the upper
layers use (`task.claim`, `task.heartbeat`, `task.setStatus`, `task.query`, …).
It does **not** define the scheduling/trigger-evaluation entry points, so the
`poll` / `patrol` / `check-all` entries in `providers.json` are a **framework-side
convention**, not part of the ACL v1 command set. Those entry scripts are
framework-owned and now ship with this repository (`team/scripts/**`); the provider
is reached through the ACL. Known gaps:

1. **No `poll` operation in the ACL.** "Claim timing belongs to poll"
   (`PROTOCOL §①`) but the ACL exposes no `poll` command — `poll` is the
   provider's trigger-evaluation entry point, referenced here by path only.
2. **Entry-path coupling — RESOLVED (shipped with the repository).** The
   `meerkat-taskpanel` entries resolve to `{team}/scripts/{poll.mjs,patrol.mjs,check-all.sh}`
   (`patrol.mjs` is patrol's decision module `patrol-scan.mjs` plus the pre-emit re-check — see
   `AUTOMATIONS.md` §3/§3.6),
   and those scripts — with their runtime dependency closure (`lib.mjs`,
   `registry.mjs`, the `check-*`/`lint-*` checks that `check-all.sh` aggregates,
   `archive.mjs`, `prototype-guard.sh`, `idem-baseline.json`) and the framework's
   own test suite — now **ship in this repository** under `team/scripts/**` and are
   deployed by `install.sh` into `{team}/scripts/**`. A fresh install no longer has
   a dangling entry path.
   **Residual (provider-side, not a framework entry-path gap) — now EXPLICIT
   (T-20261009-211234-providerdecouple):** those scripts import the provider's ACL
   library from `{team}/skills/task-ops/lib/`, which is owned by the task provider
   and **intentionally not vendored here** (`skills/PROVENANCE.md`). Without a
   provider install the entries **hard-fail** — a clear `provider 未安装：…` error
   plus non-zero exit — instead of silently degrading, so the dispatcher's
   `fire:false` now carries the cause in `state.stderr`. Likewise the `check-all.sh`
   aggregate calls the provider's contract tests under `{team}/skills/task-ops/tests/`.
3. **Envelope conformance — RESOLVED for `checkAll`.** Entries should print the
   `{fire}` envelope; `patrol.mjs` prints `{stale:[…],"dropped":[…]}` (normalized) and
   `check-all.sh` now prints a `{ok:true|false}` envelope on its last line, which
   the dispatcher normalizes (`ok:false ⇒ fire:true`). No entry degrades to
   `fire:false` solely because its output is plain text.

## Trigger-evaluation bounds (framework) vs. run lock (platform)

The dispatcher bounds **trigger evaluation only** — it is not, and cannot be, a
run-lock fix:

- `dispatch.mjs` runs the provider entry synchronously under
  `OPENCLAW_TEAM_EVAL_TIMEOUT_MS` (default **8000 ms**; invalid/absent ⇒ default),
  and `install.sh` generates each Gateway trigger with
  `exec({ command, timeoutSeconds })`. Both sit well under the Gateway's own
  **30 s** per-evaluation wall-clock budget.
- The entry gets that budget **minus `EVAL_EMIT_RESERVE_MS`** (500 ms). `install.sh`
  sizes the trigger's `timeoutSeconds` at `ceil(budget/1000)` — only ever *equal* to
  the inner bound, never larger — so a dispatcher that spent the whole budget on the
  entry would be killed by the outer `exec` before it could print anything (measured:
  empty stdout at 8008 ms). The reserve keeps the decision observable.
- A timed-out evaluation degrades (exit 0) — a broken provider never burns a model
  turn: `{"fire":false,"state":{"reason":"eval-timeout",…}}` for `poll` / `patrol`,
  and `{"fire":true,"message":…,"state":{"reason":"eval-timeout",…}}` for the
  `check-all` gate (an unconfirmed gate must alarm — see above).
- **Out of scope — platform-level:** `already-running` (a run already holding the
  job lock, so the next trigger is skipped) and the release of **stale runs** are
  **Gateway-scheduler behaviour**. The framework cannot bound or reap them; doing
  so needs owner/OpenClaw platform capability. This repository deliberately does
  **not** claim to have solved it. See `../AUTOMATIONS.md` §3.5.
- **What the framework *does* own: the run's lifetime.** Because the lock is held for
  exactly as long as a run lives, the framework-side lever on this failure mode is to
  keep the poll run **short**: `team/scripts/poll-run.mjs` is the single source for the
  poll run's payload (claim → hand off via `spawn-lane.sh` → return; never execute or
  supervise the card inside the run) and for the run bound `install.sh` registers
  (`--timeout-seconds` = one poll interval, not an hour). See `../AUTOMATIONS.md` §3.5
  and `../PROTOCOL.md` §⑥.
